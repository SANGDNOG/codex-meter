# Codex Meter V2.1 — Identity Validation

## Decision

**STOP before production schema and Dashboard implementation.**

The installed Codex App Server does not expose a safe stable account or workspace identifier through the allowed read-only `account/read { refreshToken: false }` response. The only account fields observed were `type`, `planType`, and `email`. Email is explicitly prohibited as identity material, and `type`/`planType` are neither unique nor stable account identifiers.

No V2.1 account attribution, migration, quota-by-account, or Dashboard account UI was implemented.

## Repeated Reference Account observations

Every observation returned the same privacy-safe structural schema:

| Field path | Type | Identity eligibility |
| --- | --- | --- |
| `account.type` | string | Rejected: low-cardinality auth category |
| `account.planType` | string | Rejected: shared plan category |
| `account.email` | string | Rejected: direct PII; hashing/pseudonymizing email is prohibited |

Results:

- Safe candidate count per observation: `0, 0, 0, 0, 0`
- Repeated identity status: `no_safe_candidate`
- Candidate namespace: none
- Candidate fingerprint: none
- Stability across App Server restarts: not applicable because no eligible identifier exists

## Account-change boundary observation

Only file metadata was observed as an external boundary signal; file contents were never opened.

| Signal | Before | After five probes | Result |
| --- | --- | --- | --- |
| Presence | present | present | unchanged |
| Mode | `0600` | `0600` | unchanged |
| Size | `4520` bytes | `4520` bytes | unchanged |
| Modification timestamp | same | same | unchanged |

This proves only that read-only probes did not mutate the external auth boundary. It does **not** prove that auth-file metadata is a reliable account-switch boundary.

## A → B → A result

**Not performed.** The required precondition already failed: Account A exposes no safe stable identifier. Switching accounts would at best expose another email address or the same low-cardinality fields, neither of which can be used as the final account identity. Performing login/logout work after the stop condition would add credential and account risk without enabling a compliant design.

## Cross-device result

**Not performed.** A second authenticated Codex device was not available to this experiment, and server-41 does not provide the required Node/Codex probe runtime. More importantly, cross-device equality cannot be established when the first device has no eligible identifier.

## Privacy validation

The probe:

- keeps each raw App Server response in memory only;
- emits only account field names/types, low-cardinality auth/plan labels, and HMAC fingerprints for an explicit allowlist of identifier-shaped fields;
- never fingerprints fields named as email or token/credential data;
- rejects email-like, JWT-like, malformed, nested, and ambiguous candidate values;
- stores its private probe secret and output with mode `0600`;
- contains adversarial tests proving raw email, token, account ID, nested profile value, display name, and request ID do not appear in sanitized output.

The real observation output is private and gitignored at `phase0-output/account-identity-reference.json`.

## Why the proposed production account key cannot be created

The requested formula is:

```text
SHA-256("codex-meter:v1\0" + identityNamespace + "\0" + rawStableIdentifier)
```

Both `identityNamespace` and `rawStableIdentifier` are unproven and absent in the installed App Server response. Using `email`, `planType`, auth type, auth-file hash, or a device-local synthetic value would violate the acceptance contract or fail cross-device attribution.

## Safe alternatives

1. **Preferred: upstream opaque account/workspace ID**
   Wait for or request an App Server field such as an opaque `accountId` or `workspaceId` that is stable across process restarts, account switches, and devices without exposing PII.

2. **Provider-issued privacy handle**
   Request a purpose-scoped non-credential identifier explicitly intended for local account correlation. Validate namespace semantics before use.

3. **Manual profile mode without automatic attribution**
   Allow an operator to select a local label before work starts, but treat it as user-declared metadata rather than observed account identity. Account switches cannot be detected reliably, so ambiguous intervals must remain `Unknown`. This is a materially weaker product and requires explicit approval before design.

4. **Single-account V2.0.1 continuation**
   Keep the current production model and quota reporter unchanged until a compliant identity signal exists.

The email field, an auth-file hash, and hashes of credential material are explicitly rejected alternatives.

## Re-run criteria

Repeat Phase A before resuming V2.1 only when at least one of these changes:

- Codex CLI/App Server version changes;
- `account/read` adds an opaque identifier-shaped field;
- an approved provider API exposes a purpose-scoped stable handle;
- the user explicitly approves a weaker manual-profile product contract.

A future run must still repeat the same-account restart test, A→B→A, auth-boundary comparison, and cross-device comparison before production design begins.
