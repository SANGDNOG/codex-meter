# Codex Meter V2.1 — Explicit Profile Acceptance Contract

## Identity and privacy

- Accounts are manually managed **Codex Meter local profiles**, never verified OpenAI accounts. Codex Meter never retries or performs provider-account identification.
- An account has only `id`, `name`, `created_at`, `updated_at`, `archived_at`, and a `reference` boolean. No provider email, provider identifier, token, credential, or provider account response is stored.
- The server accepts only profile UUIDs/aliases, device/profile relationships, measured usage, and profile-scoped quota. It must never receive or store `CODEX_HOME` paths, `auth.json` or a hash of it, email, provider account responses, credentials/tokens, prompts/responses, working directory, or repository path/name.
- “Reference” is administrator-maintained metadata. It is never inferred from provider state.
- CLI Agent only; Desktop is out of scope.

## Accounts and device bindings

- Device/account bindings are many-to-many entities with `id`, `device_id`, `account_id`, `codex_home_key`, `created_at`, and `disabled_at`.
- `codex_home_key` is an opaque local binding key, not a filesystem path. A sync `accountId` must be actively bound to the authenticated device; the server rejects account injection.
- Cross-device account aggregation occurs only through explicit administrator binding.
- One profile uses one dedicated `CODEX_HOME`. Home reuse or rebinding is prohibited in the MVP; archive the old profile and create a new one.

## Agent configuration and managed homes

- New Agent configuration uses `profiles: [{ accountId, name, codexHome }]`. `codexHome` remains local and is never transmitted.
- The legacy single `codexHome` configuration remains compatible as account-NULL V2.0.1 behavior during migration.
- A dedicated root determines attribution deterministically. Collection state, installation baseline, cursor, and quota state are independent per profile.
- Managed-home initialization creates a private directory and safely creates or validates `config.toml` containing `cli_auth_credentials_store = "file"`. It never overwrites conflicting existing configuration and never reads, parses, hashes, or uploads `auth.json`.
- Minimal Linux/macOS and Windows launchers set `CODEX_HOME` for a selected profile so users do not need long environment syntax.
- Users authenticate manually. Meter never invokes login/logout or an authentication API.

## Accounting and transport

- Preserve V2.0.1 semantics per profile: installation baseline, incremental `lastUsage`, stable logical event identity, at-least-once delivery, server dedupe, partial JSONL handling, archive moves, and inherited/ambiguous rollout handling.
- Stable event identity includes the stable binding/profile identity and does not duplicate after restart or archive relocation.
- Outbox and wire events include nullable `accountId`. Existing rows remain NULL; there is no backfill.
- `device_id` and `resolved_group_id` remain independent of `account_id`. Group attribution still resolves membership at `occurred_at`.
- Device and group totals are unchanged. Account totals aggregate canonical measured events, with account detail breakdowns by device and group.

## Quota

- Quota collection is profile-scoped: spawn `codex app-server --stdio` with that profile’s `CODEX_HOME` environment.
- Quota payload contains `accountId` and observed quota only, never provider identity.
- Current quota identity is at minimum `(account_id, limit_id, duration_minutes)`, so profiles cannot overwrite each other. Legacy quota is not backfilled.
- Staleness is evaluated independently per profile.
- A reference profile may use the existing dedicated server `CODEX_HOME`, but only through explicit administrator metadata and binding.

## Server schema and APIs

- Migration adds nullable `usage_events.account_id` as an account foreign key and preserves all existing NULL rows.
- Schema and APIs support account CRUD/archive/reference metadata, device/account bindings, account-scoped usage, and account-scoped current/history quota.
- Sync rejects unknown, archived, disabled, or other-device profile bindings.

## Dashboard

- Main navigation is **Overview, Groups, Devices, Accounts, Settings**.
- Accounts list shows measured usage, bound devices, quota state, and reference state.
- Device detail shows profile usage breakdown without changing its total.
- Account detail shows measured total and device/group breakdowns plus quota.
- UI consistently calls these manually managed profiles and never verified OpenAI accounts.

## Automated verification

Required automated coverage includes:

- independent roots; A/B attribution including simultaneous collection; one profile on two devices aggregates; different profiles remain separate;
- baseline per profile and new-root behavior; partial retry; archive move; stable event ID; outbox restart; server dedupe;
- unchanged device/group totals; pre-existing NULL account rows preserved; V1, Phase 0, and current V2 suites remain passing;
- independent A/B quota identity, explicit reference metadata, and independent stale state;
- privacy/adversarial rejection and scanning for paths, `auth.json`, email, provider account payloads, and credentials in payloads/logs.

## Release gate

- Real-machine validation and native Linux, macOS, and Windows release-workflow preflight are required before release readiness.
- Credential-backed real-machine tests that cannot be safely performed are recorded **NOT TESTED**. Do not invoke credential login/logout to satisfy them.
- No V2.1 release, production change, deployment, or tag occurs as part of implementation.
