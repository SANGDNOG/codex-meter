# Codex Meter V2.1 — Acceptance Contract

## Requested outcome

Evolve V2.0.1 into a privacy-preserving, multi-account usage and quota dashboard whose identity model is proven against the real Codex App Server before production schema or Dashboard work begins.

## Safety invariants

- Production V2.0.1, its database, server deployment, release assets, and installed Agents remain unchanged until the V2.1 release gate passes.
- Work occurs only on `feature/v2.1-multi-account`.
- `auth.json` and raw App Server responses are never opened by Codex Meter code, copied, logged, uploaded, or persisted.
- Never store or upload prompts, responses, reasoning, source code, file names, paths, `cwd`, repository names, tool inputs/outputs, environment variables, OAuth tokens, refresh/access tokens, or raw Codex JSONL.
- Account discovery uses only App Server `initialize`, `initialized`, and `account/read { refreshToken: false }`; quota remains `account/rateLimits/read`.
- Do not hash or pseudonymize email addresses for identity.
- Do not implement production account schema, account attribution, quota-by-account, or Dashboard account UI before Phase A establishes a safe stable identifier and account-change boundary.
- Ambiguity is represented as `Unknown`; it is never forced into the current or preceding account.
- Local account IDs stay opaque. The server receives only `accountKey = SHA-256("codex-meter:v1\0" + identityNamespace + "\0" + rawStableIdentifier)` after the identifier and namespace are empirically validated.
- Account switches create explicit boundaries. Unsynced work is finalized under the preceding known account when its evidence is unambiguous; the first observation under a new account establishes a baseline and does not inherit prior-account deltas.
- Quota is latest-only, observed-only provider truth. No estimation, prediction, pooling, or redistribution.
- Agent work is linearized under a mutex, serialized per device, transactionally outboxed, retry-safe, and idempotent by logical identity.
- Migration from V2.0.1 is one-way, transactional, rollback-safe, and idempotent; existing usage becomes `Unknown`.
- V2.1 server accepts the last V2.0.1 Agent payload during migration; old payloads map to `Unknown`. V2.1 Agent against V2.0.1 Server is explicitly incompatible.
- No release tag, production deployment, or Agent rollout before native release preflight and final Luna/xhigh review pass.

## Required Phase A evidence

1. Repeated `account/read` observations on the same Reference Account.
2. App Server process termination and restart between probes, proving candidate stability across process boundaries.
3. Safe structural field inventory and candidate fingerprinting in memory only; no raw values persisted.
4. `auth.json` is treated only as an external boundary signal via metadata where available; its contents are never read.
5. A→B→A switch and second-device observations are required before production account attribution. If unavailable in the current environment, they remain explicit blockers and production implementation stops after experiment tooling and documentation.
6. The experiment report records Codex CLI version, timestamp, platform, auth type, plan type, repeated fingerprints, boundary behavior, cross-device consistency when available, and a clear conclusion about whether a safe identifier exists.

## Required semantic behavior after Phase A succeeds

- Agent cache tracks current account key, display label, baseline validity, previous cumulative totals, current physical rollout identity, pending boundary state, and last successful observation time without retaining raw identity input.
- Usage events, quota reports, retries, and offline outbox rows carry account identity or explicit `Unknown`.
- Server schema supports accounts, account aliases, account-scoped usage, current device-account status, account quota history, and migration metadata.
- Dashboard adds Accounts plus account filters on Overview, Usage, Devices, and Quota; `Unknown` remains a first-class filter.
- Device and account usage reconcile with canonical stored facts, not duplicated mutable aggregates.

## Verification contract

- TDD: failing tests precede implementation changes.
- Unit, integration, API, migration, concurrency, retry, privacy/adversarial, mixed-version, and real environment tests cover the prompt’s matrix.
- The server migration is verified on a copy of a V2.0.1 database, including forced mid-migration failure, rollback, rerun, and idempotency.
- The actual rendered Dashboard is verified on desktop and mobile when browser automation is available.
- Linux, Windows, and macOS native Agent preflight must pass before release readiness.
- Final completion requires independent `openai-codex/gpt-5.6-luna` review at Hermes `xhigh`, followed by verified correction and final re-review if any material issue is found.

## Initial blockers that must not be guessed away

- Availability of a second Codex account for A→B→A switching.
- Availability of a second device authenticated to the same account.
- Whether the installed App Server exposes a stable, non-PII account/workspace identifier.
- Whether that identifier’s namespace is account, workspace, organization, or another scope.
